# Supabase safety protocol

1. Найди реальные таблицы, миграции, SQL-файлы, типы, Edge Functions и клиентские запросы до предложения схемы.
2. Определи, какие данные публичные, пользовательские и чувствительные.
3. Никогда не помещай `service_role` или другие секреты в переменные `VITE_*`, клиентский код, тестовые фикстуры или логи.
4. Проверяй, что доступ защищён RLS и политиками минимальных привилегий; не отключай RLS ради исправления ошибки.
5. Не запускай миграции и не меняй production без явного подтверждения пользователя.
6. Для схемных изменений описывай миграцию, совместимость старой версии клиента и откат.
7. Обрабатывай ошибки запросов; не сообщай успех, если Supabase вернул ошибку.
8. Тесты, которым нужны credentials, должны использовать отдельный тестовый проект и тестовые секреты, не production.
9. В финале перечисли, какие проверки реально выполнены и какие требуют ручной проверки в Supabase Dashboard.
