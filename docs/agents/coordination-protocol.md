# BrewMate — протокол координации AI-чатов

**Версия:** 1.0  
**Дата:** 24 ноября 2026 года  
**Область:** все специализированные чаты BrewMate и пользователь, который передаёт задачи между ними.

## 1. Назначение и ограничения

Чаты внутри одного ChatGPT Project имеют общие инструкции проекта, но отдельные истории диалогов. Нельзя предполагать, что один чат может прочитать переписку другого, увидеть его незаписанные выводы или автоматически передать ему контекст.

Поэтому координация строится на внешнем общем источнике состояния:

- **GitHub — источник истины о состоянии разработки и общий журнал координации.**
- **Context7 — источник актуальной документации библиотек и инструментов, а не хранилище задач или сообщений чатов.**
- **Пользователь — диспетчер передачи контекста между чатами и владелец решений, требующих его разрешения.**
- **Чат 00 — координатор процесса, но не привилегированный читатель других диалогов.**

Ни один чат не должен заявлять, что получил отчёт другого чата, если отчёт не был передан пользователем или опубликован в GitHub.

## 2. Роли инструментов

### GitHub

Использовать GitHub для фиксации долговременного состояния:

- **Issues** — постановка задач, владелец/ответственная специализация, scope, критерии приёмки, зависимости, ограничения по файлам и статус.
- **Pull Requests** — конкретные изменения, обсуждение, review, CI и доказательства.
- **Commits и branches** — точная история изменений и изоляция параллельной работы.
- **Markdown-документы в репозитории** — продуктовые решения, архитектурные решения, протоколы и знания, которые должны пережить отдельный чат.
- **CI** — проверяемые результаты автоматических проверок.

Не использовать сообщения чатов как единственное место хранения решения, которое влияет на другие специализации.

### Context7

Context7 применяется для получения актуальной документации по конкретной библиотеке, фреймворку, SDK или инструменту, когда задача зависит от его API или поведения.

Порядок использования:

1. Определи конкретную библиотеку/продукт и вопрос, который нужно проверить.
2. Если точный Context7 Library ID не предоставлен, сначала разреши название библиотеки через Context7 Resolve Library ID.
3. Выбери точное совпадение по названию, репутации источника, покрытию документации и версии.
4. Запроси документацию по одному конкретному концепту за вызов.
5. Сверь пример с фактической версией зависимости в package.json/lockfile и с кодом BrewMate.
6. Зафиксируй в Issue/PR, какую документацию и версию использовал, если она повлияла на решение.

Context7 не подтверждает состояние репозитория, не заменяет чтение исходников и тестов, не является хранилищем проектных решений и не синхронизирует чаты. Не используй его для поиска внутренних файлов BrewMate или приватных данных проекта.

Если документация Context7 расходится с фактическим поведением установленной версии или кодом, зафиксируй расхождение и проверь его отдельным тестом/экспериментом.

## 3. Жизненный цикл задачи через GitHub

### 3.1 Постановка

До начала реализации координатор или пользователь создаёт GitHub Issue. Для небольшого документационного изменения допустима задача в существующем PR, если scope и владелец однозначны.

Issue должна содержать:

- **Цель / проблема**
- **Ответственная специализация и ведущий чат**
- **Контекст и ссылки на решения**
- **Scope**
- **Вне scope**
- **Критерии приёмки**
- **Зависимости**
- **Риски**
- **Разрешённые файлы/модули**
- **Файлы/модули, зарезервированные другими задачами**
- **Ожидаемые проверки**
- **Связанный PR** (после создания)

Не назначать задачу двум чатам как совместную реализацию. Для параллельной работы декомпозировать её на независимые задачи с непересекающимися файлами и интерфейсами.

### 3.2 Захват задачи и владение

Перед работой агент обязан:

1. Открыть Issue и проверить, что задача ещё актуальна и не закрыта.
2. Проверить открытые PR и недавние коммиты по затрагиваемым файлам.
3. Проверить, не зарезервированы ли те же файлы другим активным исполнителем.
4. Оставить комментарий в Issue о начале работы: чат/специализация, ветка, предполагаемые файлы и базовый SHA.
5. Создать отдельную ветку от актуальной целевой базы, если задача предполагает кодовые/документационные изменения.
6. Не начинать работу, если владение конфликтует. Сначала согласовать передачу или разделить scope.

Один Issue/PR имеет одного ведущего исполнителя. Другие специализации могут проводить review или давать рекомендации, но не должны одновременно редактировать ту же ветку.

### 3.3 Реализация и PR

PR должен ссылаться на Issue и содержать:

- краткое описание результата;
- scope и сознательно не затронутые области;
- список изменённых файлов/модулей;
- решения и важные допущения;
- тесты и проверки с фактическим результатом;
- непроверенные сценарии;
- риски и ограничения;
- следующий шаг/handoff.

По умолчанию PR создаётся Draft, если задача ещё требует согласования или review. Создание PR не означает разрешения на merge или deploy.

### 3.4 Завершение и освобождение владения

После завершения агент публикует итоговый комментарий в Issue/PR:

- статус DONE / PARTIAL / BLOCKED / PROPOSAL;
- ветка, PR и точный HEAD commit SHA;
- изменённые файлы;
- реально выполненные проверки и ссылки на CI;
- что осталось непроверенным;
- риски и зависимости;
- что следующему исполнителю не нужно повторять;
- следующий конкретный шаг.

Владение файлами считается освобождённым только после явной записи в Issue/PR о завершении или передаче. Если задача частичная, перечислить файлы, которые всё ещё заняты, и оставшиеся действия.

Не закрывать Issue до выполнения критериев приёмки и согласованного завершения. Не мержить PR и не выполнять deploy без отдельного явного разрешения пользователя.

## 4. Передача контекста между чатами

Поскольку чаты не видят историю друг друга, передача выполняется через GitHub и пользователя:

1. Исполнитель записывает результат и handoff в Issue/PR.
2. Пользователь переносит ссылку и краткое резюме в следующий чат.
3. Получающий чат открывает актуальные Issue, PR, ветку и файлы в GitHub.
4. Получающий чат проверяет HEAD SHA и статус CI заново.
5. Получающий чат продолжает только согласованную часть задачи и публикует собственный результат.

Текст, скопированный пользователем, служит навигацией, но не заменяет проверку GitHub. Если отчёт в чате и состояние GitHub расходятся, приоритет имеет актуальное состояние репозитория и CI; конфликт нужно явно сообщить.

## 5. Ответственность чата 00 — координатора

Чат 00 должен:

- проверять актуальные Issues, PR, ветки, коммиты и CI через GitHub;
- поддерживать приоритеты и зависимости;
- создавать задачи с одним ведущим исполнителем;
- указывать владельцев и непересекающиеся файловые области;
- выявлять дублирующие задачи и конфликтующие изменения;
- собирать решения в Issues, PR и документации;
- формировать для пользователя готовый handoff в нужный специализированный чат.

Чат 00 не может автоматически читать другие диалоги и не должен утверждать, что собрал их результаты, пока они не опубликованы в GitHub или не переданы пользователем.

## 6. Правила использования Context7 и GitHub вместе

- GitHub отвечает на вопрос **«что сейчас реализовано и что команда решила?»**
- Context7 отвечает на вопрос **«как документированно работает используемая библиотека/SDK и каков актуальный API?»**
- Исходники, lockfile, тесты и CI отвечают на вопрос **«совместимо ли это с конкретной версией и нашим приложением?»**
- Issue/PR/ADR отвечает на вопрос **«какое решение принято и почему?»**

Нельзя обосновывать архитектурное изменение только фрагментом документации Context7. Нельзя использовать старый комментарий в GitHub как подтверждение текущего состояния кода без проверки актуального HEAD.

## 7. Эскалация и разрешение конфликтов

Немедленно остановить затрагивающие конфликт файлы изменения и сообщить пользователю/координатору, если:

- два активных чата заявили владение одной веткой или файлами;
- обнаружен несовместимый API/data contract;
- новая работа требует миграции или изменения синхронизации;
- найден риск потери пользовательских данных или ослабления безопасности;
- продуктовые требования противоречат Product Vision или явному решению пользователя;
- CI/тесты не подтверждают заявленный результат.

Координатор фиксирует конфликт и предлагает варианты. Изменение публичного контракта, схемы данных, политики безопасности, продуктового направления, merge и production deploy требуют предусмотренного регламентом согласования.

```md
**Статус:** DONE / PARTIAL / BLOCKED / PROPOSAL  
**Issue:**  
**PR:**  
**Ветка:**  
**HEAD SHA:**  
**Изменённые файлы:**  
**Что сделано:**  
**Проверки и CI:**  
**Что не проверено:**  
**Риски / зависимости:**  
**Что не нужно повторять:**  
**Следующий чат / специализация:**  
**Следующий конкретный шаг:**  
```

Главное правило: **контекст, необходимый другому чату, должен быть опубликован в GitHub; Context7 используется для технической документации, а не как замена общей памяти.**
